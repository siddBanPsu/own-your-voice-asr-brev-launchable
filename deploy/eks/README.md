# Deploy the customized Riva ASR pipeline on Amazon EKS

This is the production-oriented Lab 3 path. It assumes an existing EKS cluster
with homogeneous NVIDIA GPU nodes, `kubectl`, Helm, a storage class, and NGC
entitlement. Cluster creation is intentionally outside the attendee lab because
it changes AWS infrastructure and usually takes longer than the model exercise.

The deployable input is `artifacts/riva/own_your_voice_asr.rmir`, generated by
`scripts/build_riva_rmir.sh`. The RMIR is hardware-independent; the Riva Helm
chart runs `riva-deploy` on the target GPU and creates the optimized Triton model
repository there.

## 1. Validate the EKS GPU boundary

```bash
aws sts get-caller-identity
kubectl cluster-info
kubectl get nodes -o=custom-columns=NAME:.metadata.name,GPU:.status.allocatable.nvidia\.com/gpu,GPU_PRODUCT:.metadata.labels.nvidia\.com/gpu\.product
```

For EKS managed node groups using the NVIDIA device plugin, GPU nodes should
advertise `nvidia.com/gpu`. New Kubernetes 1.34+ managed-node deployments may
instead use NVIDIA DRA; follow the current AWS EKS GPU-device guidance for the
cluster rather than installing both mechanisms on the same nodes.

## 2. Fetch the pinned Riva chart

```bash
export RIVA_VERSION=2.26.0
export NGC_API_KEY='<personal NGC key>'
helm fetch "https://helm.ngc.nvidia.com/nvidia/riva/charts/riva-api-${RIVA_VERSION}.tgz" \
  --username='$oauthtoken' --password="${NGC_API_KEY}" --untar
```

Do not commit the API key or a rendered Kubernetes Secret.

## 3. Stage the custom RMIR on the chart's model volume

Use a persistent volume supported by the cluster and mount it as `/data` in a
temporary staging pod. Copy the RMIR to the exact Riva custom-model layout:

```text
/data/rmir/own_your_voice_asr_v1.0/model.rmir
```

In the fetched chart's `values.yaml`, enable the external PVC using the current
`persistentVolumeClaim` fields. For a single-node rehearsal, `ReadWriteOnce` is
enough. For replicas across nodes, use shared storage such as an EFS-backed
`ReadWriteMany` claim, or configure the chart's S3 model cache. Optimized model
caches are GPU-specific, so keep every replica on the same GPU product.

## 4. Select only the customized ASR model

Merge `values-custom-rmir.yaml` into the fetched chart values. Confirm that the
final `modelRepoGenerator.ngcModelConfigs.tritonGroup0.models` contains only:

```yaml
- own_your_voice_asr:1.0
```

The directory name, model entry, and version must match. Disable NLP and TTS to
avoid downloading unused models and consuming extra GPU memory.

## 5. Install and verify

```bash
helm upgrade --install riva-api ./riva-api \
  --namespace riva --create-namespace \
  --values deploy/eks/values-custom-rmir.yaml \
  --set-string ngcCredentials.password="${NGC_API_KEY}" \
  --set-string modelRepoGenerator.modelDeployKey="$(printf '%s' tlt_encode | base64 | tr -d '\n')"

kubectl get pods,svc -n riva -w
kubectl logs -n riva -l app.kubernetes.io/instance=riva-api -c riva-model-init --tail=100
kubectl port-forward -n riva service/riva-api 50051:50051
```

Run the same Riva Python client cell from Lab 3 against `localhost:50051`. For
external production traffic, use an ingress or load balancer that supports
HTTP/2 and gRPC, then add TLS, health checks, metrics, authorization, and
workload-based autoscaling. Do not expose Triton's internal ports as the public
application contract; clients should use the Riva gRPC API on port 50051.

Before installation, inspect the pinned chart with `helm show values` because
storage-class, node-selector, and ingress details belong to the target EKS
cluster and must not be guessed in a portable workshop repository.
